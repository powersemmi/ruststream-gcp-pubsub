# Ключи упорядочивания

Это руководство сохраняет порядок сообщений одного ключа: при получении, при параллельной обработке внутри сервиса и при публикации.

По умолчанию Pub/Sub доставляет сообщения в произвольном порядке.
Сообщение, опубликованное с ключом упорядочивания в подписку с упорядочиванием сообщений, приходит после всех более ранних сообщений того же ключа.
Сообщения разных ключей по-прежнему приходят в любом порядке, и поэтому их можно обрабатывать параллельно.
Гарантия действует для сообщений, опубликованных в одном регионе.

Пример - сервис бухгалтерской книги: проводка меняет баланс одного счёта, и проводки одного счёта должны применяться по порядку.
Сервис счетов публикует каждую проводку с идентификатором счёта в качестве ключа упорядочивания.

[`create_with_topic`](../components/subscriptions/create-with-topic.md) создаёт `ledger-posting` с упорядочиванием сообщений.
Pub/Sub фиксирует эту настройку при создании подписки, поэтому у подписки, которой владеет эксплуатация, она есть, только если её включила эксплуатация.

`workers(8, by_key)` обрабатывает до восьми проводок одновременно на восьми партициях воркеров.
Все проводки одного счёта попадают на одну партицию воркеров, и она обрабатывает их одну за другой.
Поэтому счета проводятся параллельно, а проводки одного счёта сохраняют порядок.
Доставка сообщает свой ключ упорядочивания в заголовке [`partition-key`](../components/publishing/ordering/partition-key.md), и именно его читают партиции воркеров.
В ручной форме партиции воркеров задаёт шаг цепочки `workers_by_key`.

При повторной доставке сообщения одного ключа Pub/Sub снова доставляет и более поздние сообщения этого ключа, поэтому обработчик упорядоченной подписки должен быть идемпотентным.

## Ключ на том, что публикует сервис

`post` публикует проведённую проводку в `postings` под ключом счёта, который называет в вызове шаг [`ordering_key`](../components/publishing/ordering/ordering-key.md).
Шаг приходит с прелюдией. Чтобы он был доступен, параметр `Out` называет тип настроек крейта: `Publisher<Options = PubSubPublishOptions>`.
Публикация без ключа не упорядочивается.

У ответа нет вызова, в котором можно назвать ключ.
Ключ для каждой доставки задаёт [преобразование публикации](../components/publishing/ordering/transform.md):

`UnderTheEntrysKey` читает ключ, с которым пришла проводка, и передаёт его выписке, поэтому выписки одного счёта тоже сохраняют порядок.
Ключ, одинаковый для всех сообщений точки монтирования, задаётся вместо этого в политике: [`Publish::default().ordering_key(..)`](../components/publishing/ordering/policy.md).
Если ключ задан в нескольких местах, вызов важнее заголовка `partition-key`, а заголовок важнее политики.

Неудачная публикация с ключом приостанавливает этот ключ в клиенте. Крейт возобновляет его, поэтому следующая публикация ключа отправляется, а обработчик получает ошибку.
На эмуляторе создайте темы `postings` и `statements` до запуска сервиса, как в руководстве [Публикация и ответы](publishing.md#running-it).

## Тестирование

Тесты публикуют проводку с ключом счёта в заголовке `partition-key`: так ключ сервиса счетов доходит до доставки.
Ключ проведённой проводки они проверяют через `tb.out::<DefaultSlot>().with_options(..)`, а ключ выписки - через `published(..).with_options(..)`.
Внутрипроцессный Pub/Sub не моделирует упорядоченную доставку. Тест на эмуляторе для неё есть на [странице компонента упорядочивания](../components/publishing/ordering/index.md).
