    Ordering keys

    This guide keeps the messages of one key in order: on the way in, through the service's own concurrency, and on the way out.

    Pub/Sub delivers messages in no particular order by default. A message published with an ordering key, to a subscription with message ordering on, arrives after every earlier message of the same key. Messages of different keys still arrive in any order, and that is what lets them be handled side by side. The guarantee holds for messages published to one region.

    The example is a ledger service: an entry changes the balance of one account, and the entries of one account must apply in order. The account service publishes each entry with the account's id as its ordering key.

    Ordered delivery, handled in lanes​

    src/main.rs
    /// The entries of one account reach one lane in publish order; eight lanes run side by side.
    #[subscriber(
        GooglePubSub::new("ledger-posting").create_with_topic("ledger"),
        workers(8, by_key)
    )]
    async fn post(
        entry: &Entry,
        Out(out): Out<impl Publisher<Options = PubSubPublishOptions>>,
    ) -> HandlerOutcome {
        let posted = Posted {
            account: entry.account.clone(),
            amount_cents: entry.amount_cents,
        };
        let sent = out
            .message(&posted)
            .to("postings")
            .ordering_key(entry.account.clone())
            .publish()
            .await;
        match sent {
            Ok(()) => HandlerOutcome::ack(),
            Err(err) => {
                tracing::warn!(entry.account, error = %err, "posting not published, entry retried");
                HandlerOutcome::retry()
            }
        }
    }
    src/main.rs
    /// Posts an entry and publishes the posting under the account's key.
    struct Post;

    impl<Slot> Handle<Entry, (), Outs<(Slot,)>> for Post
    where
        Slot: OutEntry<DefaultSlot, Wire: Publisher<Options = PubSubPublishOptions>>,
    {
        async fn handle(
            &self,
            entry: &Entry,
            outs: &Outs<(Slot,)>,
            _ctx: &mut Context<'_>,
        ) -> Result<(), HandlerOutcome> {
            let posted = Posted {
                account: entry.account.clone(),
                amount_cents: entry.amount_cents,
            };
            let sent = outs
                .get(DefaultSlot)
                .message(&posted)
                .to("postings")
                .ordering_key(entry.account.clone())
                .publish()
                .await;
            if let Err(err) = sent {
                tracing::warn!(entry.account, error = %err, "posting not published, entry retried");
                return Err(HandlerOutcome::retry());
            }
            Ok(())
        }
    }

    create_with_topic creates ledger-posting with message ordering on. Pub/Sub fixes that setting when the subscription is created, so a subscription operations own has it only if they turned it on.

    workers(8, by_key) handles up to eight entries at once in eight lanes. Every entry of one account goes to the same lane, and a lane handles its entries one after another. So the accounts are posted side by side, and the entries of one account keep their order. A delivery reports its ordering key in the partition-key header, which is the key the lanes read. In the manual form the lanes are the workers_by_key step of the chain.

    When a delivery of one key is redelivered, Pub/Sub delivers the later messages of that key again too, so a handler of an ordered subscription is idempotent.

    The key on what the service publishes​

    post publishes the posted entry to postings under the account's key, named on the call with the ordering_key step. The step comes with the prelude, and it needs the Out parameter to name the crate's settings type, Publisher<Options = PubSubPublishOptions>. A publish without a key carries no ordering.

    A reply has no call to name a key on. A publish transform sets it per delivery:

    src/main.rs
    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing)]
    #[outgoing(name = "statements")]
    struct Statement {
        account: String,
        amount_cents: i64,
    }

    /// Answers each entry with a statement line for the account's owner.
    #[subscriber(GooglePubSub::new("ledger-statements").create_with_topic("ledger"), reply)]
    async fn notify(entry: &Entry) -> Statement {
        Statement {
            account: entry.account.clone(),
            amount_cents: entry.amount_cents,
        }
    }

    /// Sends each reply under the key of the entry it answers, which the delivery reports in its
    /// `partition-key` header.
    struct UnderTheEntrysKey;

    impl<C> PublishTransform<ForReply<C>, PubSubPublishOptions> for UnderTheEntrysKey {
        type Destination = Reads;

        fn apply(
            &self,
            _out: &mut Outgoing<'_>,
            options: &mut Option<PubSubPublishOptions>,
            cx: &PublishContext<'_, C>,
        ) {
            if let Some(key) = cx.headers().get_str(PARTITION_KEY_HEADER) {
                options
                    .get_or_insert_with(PubSubPublishOptions::default)
                    .ordering_key = Some(key.to_owned());
            }
        }
    }
    src/main.rs
    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing, JsonSchema)]
    #[schemars(crate = "ruststream::schemars")]
    #[outgoing(name = "statements")]
    struct Statement {
        account: String,
        amount_cents: i64,
    }

    /// Answers each entry with a statement line for the account's owner.
    struct Notify;

    impl Handle<Entry, Statement> for Notify {
        fn handle(
            &self,
            entry: &Entry,
            _outs: &(),
            _ctx: &mut Context<'_>,
        ) -> impl Future<Output = Result<Statement, HandlerOutcome>> {
            ready(Ok(Statement {
                account: entry.account.clone(),
                amount_cents: entry.amount_cents,
            }))
        }
    }

    /// Sends each reply under the key of the entry it answers, which the delivery reports in its
    /// `partition-key` header.
    struct UnderTheEntrysKey;

    impl<C> PublishTransform<ForReply<C>, PubSubPublishOptions> for UnderTheEntrysKey {
        type Destination = Reads;

        fn apply(
            &self,
            _out: &mut Outgoing<'_>,
            options: &mut Option<PubSubPublishOptions>,
            cx: &PublishContext<'_, C>,
        ) {
            if let Some(key) = cx.headers().get_str(PARTITION_KEY_HEADER) {
                options
                    .get_or_insert_with(PubSubPublishOptions::default)
                    .ordering_key = Some(key.to_owned());
            }
        }
    }

    UnderTheEntrysKey reads the key the entry arrived with and gives it to the statement, so the statements of one account stay in order too. A key that is the same for every message of a mount site goes on the policy instead: Publish::default().ordering_key(..). Where several name one, the call wins over the partition-key header, and the header over the policy.

    #[ruststream::app]

    fn app() -> impl App {
        RustStream::new(AppInfo::new("ledger", "0.1.0")).with_broker(
            PubSubBroker::new("my-project").emulator("localhost:8085"),
            |b| {
                // The entries of one account reach one lane in publish order; eight lanes run side
                // by side.
                b.include(
                    subscriber(
                        GooglePubSub::new("ledger-posting").create_with_topic("ledger"),
                        Post,
                    )
                    .workers_by_key(nonzero!(8))
                    .build(),
                )
                .out(DefaultSlot, Publish::default())
                .build();
                b.include(
                    subscriber(
                        GooglePubSub::new("ledger-statements").create_with_topic("ledger"),
                        Notify,
                    )
                    .reply()
                    .build(),
                )
                .out_reply(Publish::default())
                .transform(UnderTheEntrysKey);
            },
        )
    }

    fn main() -> ExitCode {
        run_main(app)
    }

    A failed publish with a key pauses that key in the client; the crate resumes it, so the next publish of the key goes out, and the failure reaches the handler as an error. Against the emulator, create the topics postings and statements before the service starts, as in Publishing and replies.

    Testing​

    The tests publish an entry with the account's key in the partition-key header, the way the account service's key reaches a delivery. They check the key on the posting with tb.out::<DefaultSlot>().with_options(..), and on the statement with published(..).with_options(..). The in-process Pub/Sub does not model ordered delivery; the ordering component page holds a test of it against the emulator.
