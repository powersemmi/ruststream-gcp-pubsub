# Google Cloud Pub/Sub

`ruststream-gcp-pubsub` запускает сервис RustStream на Google Cloud Pub/Sub поверх официального
клиента [`google-cloud-pubsub`](https://docs.rs/google-cloud-pubsub). Pub/Sub разделяет тему и
подписку: сервис публикует в тему, а обработчик читает подписку, которая копит для него сообщения
этой темы. Понятия фреймворка (подписчики, маршрутизация, кодеки, middleware) описаны в
[документации RustStream](https://powersemmi.github.io/ruststream/).

```toml
ruststream = { version = "0.7", features = ["macros", "json"] }
ruststream-gcp-pubsub = "0.7"
serde = { version = "1", features = ["derive"] }
```

## Совместимости {#capabilities}

Необязательные совместимости фреймворка на Pub/Sub:

| Совместимость | Нативно | Примечания |
| --- | --- | --- |
| `Subscribe` | да | вы подписываетесь по [имени подписки](#subscriptions) |
| `BatchSubscriber` | на клиенте | обработчик среза получает [пакеты, собранные на клиенте](#batches) |
| `TransactionalPublisher` | нет | серию сообщений группирует [ключ упорядочивания](#ordering-keys) |
| `OwnedTransactions` | нет | транзакции публикации, которой можно владеть, здесь нет |
| `RequestReply` | нет | вы собираете его сами из темы для ответов и атрибута корреляции |
| `Partitioned` | да | [ключ партиционирования - это ключ упорядочивания сообщения](#ordering-keys) |
| `Seekable` и `Positioned` | нет | подписку целиком вы перемещаете административным вызовом `seek` - на момент времени или на снимок |
| `DescribeServer` | да | сообщает используемые хост и порт (эмулятор, свой адрес сервиса или `pubsub.googleapis.com`) под протоколом `googlepubsub`; схема, путь и учётные данные, вписанные в адрес, в документ не попадают |

Ключ упорядочивания обработчик читает из доставки вызовом `message.partition_key()` и ничего для
этого из крейта не импортирует.

## Жизненный цикл {#the-lifecycle}

Каждое состояние брокера - отдельный тип, и переход к следующему состоянию поглощает предыдущее:

```text
PubSubBroker::new(project)   только конфигурация, синхронно, без ввода-вывода
  .connect()   ->  ConnectedPubSubBroker    живые клиенты; подписки и издатели
  .shutdown()  ->  ()                       сбрасывает все накопленные пакеты публикаций
```

`shutdown` поглощает подключённый брокер, поэтому публикация или подписка после него не
скомпилируется. Издатель, выданный раньше, под эту гарантию не попадает: как только соединения не
стало, он возвращает `PubSubError::NotConnected` вместо того, чтобы принять сообщение, которое
никто не отправит.

По умолчанию брокер аутентифицируется через Application Default Credentials. `credentials(..)`
берёт вместо них ваши собственные `google_cloud_auth::credentials::Credentials`. `endpoint(..)`
задаёт другой адрес сервиса, в том числе региональный. `emulator(host)` направляет все клиенты на
локальный [эмулятор](#the-emulator).

## Подписки {#subscriptions}

`GooglePubSub` называет подписку, которую читает обработчик, - коротким идентификатором или полным
именем ресурса `projects/{project}/subscriptions/{name}`. Он стоит внутри атрибута
`#[subscriber(..)]`:

```rust
--8<-- "crates/ruststream-gcp-pubsub/examples/pubsub_service.rs:handler"
```

Точка монтирования связывает обработчик с брокером:

```rust
--8<-- "crates/ruststream-gcp-pubsub/examples/pubsub_service.rs:app"
```

У дескриптора четыре настройки:

- `create_with_topic(topic)` создаёт подписку и её тему при подписке, если их ещё нет. Он нужен для
  локальной разработки и тестов против [эмулятора](#the-emulator); боевой подпиской обычно
  управляет инфраструктура.
- `max_outstanding(n)` управляет потоком: сколько доставленных сообщений могут оставаться
  неподтверждёнными одновременно. Это и есть настоящая предвыборка, по умолчанию - клиентские 1000.
- `ack_extension(duration)` - насколько далеко каждое фоновое продление отодвигает срок
  подтверждения, пока работает обработчик. Клиент зажимает значение в протокольный диапазон от 10
  до 600 секунд, по умолчанию - 60 секунд.
- `batch_wait(duration)` - сколько неполный [пакет](#batches) ждёт новых доставок. По умолчанию -
  50 мс.

Дескриптор с пустым именем подписки или темы возвращает `PubSubError::InvalidDescriptor` до всякого
ввода-вывода.

Подписка читается в режиме streaming pull. Пока работает обработчик, клиент продлевает срок
подтверждения в фоне, поэтому медленный обработчик сам по себе не вызывает повторной доставки.
Удаление подписчика опустошает поток.

`#[subscriber("orders-workers")]` с обычной строкой называет тот же дескриптор с его умолчаниями,
поэтому подписка должна существовать заранее.

Подписку определяет только её имя, поэтому назвать его может точка монтирования:
`#[subscriber(GooglePubSub)]` на обработчике и `.name("orders-workers")` там, где он монтируется.
Так один обработчик обслуживает два развёртывания, которые различаются только именем подписки.

## Пакеты {#batches}

Обработчику, который принимает срез, отдают целый пакет: одно обращение к базе и один пакетный
вызов API на пакет, а не на заказ.

```rust
--8<-- "crates/ruststream-gcp-pubsub/examples/pubsub_batches.rs:handler"
```

Размер пакета называет точка монтирования, и без него пакетный обработчик не монтируется:

```rust
--8<-- "crates/ruststream-gcp-pubsub/examples/pubsub_batches.rs:app"
```

Streaming pull отдаёт по одной доставке за раз, поэтому пакеты собираются на клиенте. В пакете
никогда не больше сообщений, чем назвала точка монтирования, и может быть меньше.

Размер - одна половина пакета, вторая - `batch_wait` на дескрипторе, и его умолчание в 50 мс -
это примерно одна порция streaming pull. Меньше - и большинство пакетов закроются на первой же
доставке. Больше - и тихая подписка будет впустую придерживать пакет. Поднимайте его, когда пакет
окупает сетевое обращение.

`max_outstanding` ограничивает выборку, а не пакет.

`PubSubTestBroker` собирает пакеты так же, поэтому обработчик среза можно
[тестировать внутри процесса](#testing), а не только против эмулятора.

## Подтверждение {#acknowledgement}

Подтверждение нативное и отдельное для каждого сообщения:

| Исход обработчика | Вызов Pub/Sub | Что происходит |
| --- | --- | --- |
| `HandlerOutcome::ack()` | acknowledge | доставка завершена |
| `HandlerOutcome::retry()` | nack | сообщение снова становится доступным и доставляется повторно |
| `HandlerOutcome::drop()` | acknowledge | сообщение повторно не доставляется |

В Pub/Sub нет операции «отбросить без повторной доставки», поэтому `drop()` подтверждает сообщение.
Poison-сообщения разводит политика dead-letter, заданная на ресурсе подписки. Под такой политикой
число попыток доставки приходит в заголовке `pubsub-delivery-attempt` (он экспортирован как
`DELIVERY_ATTEMPT_HEADER`), и обработчик может ветвиться по тому, сколько раз сообщение
возвращалось.

Отложенного nack в Pub/Sub нет, поэтому `HandlerOutcome::retry_after(delay)` работает через
[отложенную повторную публикацию](https://powersemmi.github.io/ruststream/latest/guides/subscribers/#delayed-redelivery)
рантайма: свяжите с областью издателя вызовом `retry_via`, взяв его из `b.broker().publisher()`.
Рантайм тогда подтверждает доставку и публикует копию сообщения после задержки. Без такого издателя
задержка теряется, сообщение сразу возвращается в очередь, а рантайм пишет предупреждение.

Копия уходит в тему, к которой привязана подписка, а не на имя подписки: публикация в Pub/Sub
адресуется теме. Эту тему сообщает `GooglePubSub` - ту, которую называет `create_with_topic`, или
ту, которую API отдаёт для подписки, управляемой инфраструктурой; спрашивают её один раз на старте.
Обработчик, объявленный обычной строкой, назвать тему не может, потому что имя подписки никуда не
ведёт, поэтому область, где `retry_via` связан поверх `#[subscriber("orders-workers")]`,
отказывается стартовать и называет подписку. Лечится это объявлением того же обработчика через
`GooglePubSub::new("orders-workers")`.

### Подтверждение exactly-once {#exactly-once-acknowledgement}

Доставка exactly-once - это настройка ресурса подписки, поэтому на обоих видах подписки работает
один и тот же код обработчика. На подписке exactly-once `ack` возвращает `Ok` только после того,
как сервис его подтвердил, и после этого сообщение повторно не доставляется. Отклонённое
подтверждение (истёкший ack id, проигранная гонка со сроком) возвращает `AckError::Broker`, а не
проходит как успех. На обычной подписке `ack` возвращает `Ok`, как только подтверждение поставлено
в очередь.

## Ключи упорядочивания {#ordering-keys}

Сообщения с одним ключом упорядочивания приходят одному подписчику в порядке публикации. Ключ - это
поле сообщения, а не заголовок, и это единственная настройка публикации в Pub/Sub помимо полезной
нагрузки и атрибутов. `PubSubPublishOptions` - эта настройка в виде типа, и `ordering_key` - его
единственное поле.

Ключ попадает в публикацию из двух мест. Точка монтирования закрепляет его за целым слотом, и
именно это нужно слоту, который принадлежит одной сущности:

```rust
--8<-- "crates/ruststream-gcp-pubsub/examples/pubsub_ordered_publish.rs:ordered"
```

Отдельная публикация называет свой ключ шагом `ordering_key`, между `message(..)` и `publish()`.
Шаг стоит на билдере публикации фреймворка, поэтому завершённая им публикация сохраняет всё
остальное, что решила точка монтирования: кодек, названный этой записью, её преобразования и слот,
на который смотрит тест.

Тело обработчика, которое называет этот шаг, импортирует прелюдию этого крейта и объявляет это в
сигнатуре - единственное место, где тело называет брокер, на котором работает:

```rust
--8<-- "crates/ruststream-gcp-pubsub/examples/pubsub_ordered_publish.rs:handler"
```

Телу, которое ключа не называет, не нужно ни то ни другое: оно отправляет под тем ключом, который
закрепила точка монтирования.

У ответа нет места вызова, поэтому его ключ - ключ политики:
`.out(Reply, Publish::default().ordering_key("receipts"))`. Ключ, свой у каждого ответа, задаёт
`.transform(..)` в цепочке монтирования: он читает доставку и пишет заголовок `partition-key`
ответа.

На стороне доставки ключ партиционирования фреймворка *и есть* ключ упорядочивания: доставка отдаёт
его через `message.partition_key()` и в заголовке `partition-key` (он экспортирован как
`PARTITION_KEY_HEADER`), поэтому обработчик, который читает ключи, ничего из этого крейта не
импортирует. Тот же заголовок задаёт ключ и на отправке - для сервиса, написанного без привязки к
брокеру: заголовок на исходящем сообщении упорядочивает это сообщение, а вызов, назвавший шаг,
имеет приоритет над ним. Атрибутом этот заголовок не передаётся.

Упорядоченной доставке нужно включённое упорядочивание сообщений на подписке. Региональный
`endpoint` - это то, что держит один ключ упорядоченным между издателями внутри одного региона.
Публикация, вернувшая ошибку на упорядоченном ключе, ставит этот ключ на паузу в клиенте; крейт
снимает паузу и возвращает ошибку, поэтому один сбой не блокирует все последующие публикации по
этому ключу.

Любой другой заголовок - это атрибут сообщения, в обе стороны и без всякого конверта вокруг,
поэтому собеседник не на Rust видит обычное сообщение Pub/Sub.

## Публикация {#publishing}

`PubSubPublish` - политика, которая конструирует издателя `PubSubPublisher`, и рантайм инстанцирует
его на старте на подключённом брокере. Она же - политика брокера по умолчанию, поэтому отвечающий
обработчик, смонтированный без вызова `.out(Reply, ..)`, публикует через неё.

Файл с телами обработчиков импортирует только прелюдию фреймворка и ограничивает слот
совместимостью: `Out(out): Out<impl Publisher>`. Такой файл не называет брокер. Исключение - тело,
которое называет [ключ упорядочивания](#ordering-keys) для каждого сообщения.

Файл маршрутов импортирует `ruststream_gcp_pubsub::prelude::*`, где политика лежит под именем точки
монтирования `Publish`: `.out(Reply, Publish::default())` - для значения, которое возвращает
отвечающий обработчик, `.out(Marker, Publish::default())` - для слота `Out`, а `.ordering_key(..)`
на политике - там, где упорядочен весь слот. `PubSubPublish` остаётся в корне крейта для файла,
который говорит сразу с двумя брокерами и должен сказать, какой из них имеет в виду.

Публикация адресуется теме - по идентификатору или по полному имени ресурса. Клиентский издатель
темы создаётся при первом обращении и кешируется на брокере, поэтому `shutdown` сбрасывает все
накопленные им пакеты.

`ordering_key` - единственное, что этот крейт добавляет в цепочку публикации фреймворка. Сообщение
Pub/Sub - это полезная нагрузка, её атрибуты и ключ упорядочивания, поэтому цепочка покрывает все
три части: значение, его заголовки и ключ.

Сообщение, собранное вручную и переданное в `Publisher::publish`, уходит таким, каким его собрали:
так вы сами управляете ассоциативным массивом заголовков.

## Эмулятор {#the-emulator}

`emulator(host)` направляет брокер на локальный эмулятор Pub/Sub: незашифрованный адрес и анонимные
учётные данные одним вызовом. Клиент не читает `PUBSUB_EMULATOR_HOST`, поэтому назовите хост сами.

```bash
just brokers-up    # docker compose up: gcloud beta emulators pubsub start на 8085
cargo run --example pubsub_service
just brokers-down
```

Эмулятор стартует пустым - для этого и нужен `create_with_topic`: подписка и её тема создаются при
подписке. Два сервиса, гонящиеся за одними и теми же именами, оба оказываются подключены, потому
что создание - это чтение, затем создание, затем снова чтение.

Набор живых тестов запускается так же и включается переменной `PUBSUB_TEST_HOST`:

```bash
just test-brokers  # поднимает эмулятор, гоняет интеграционные наборы и conformance
```

## Тестирование {#testing}

Фича `testing` поставляет `PubSubTestBroker` - внутрипроцессный транспорт, который воспроизводит
маршрутизацию крейта. Смонтируйте сервис на нём и управляйте им через обвязку `TestApp`
фреймворка. Тестовый файл называет оба типа по пути, рядом с glob прелюдии:
`use ruststream_gcp_pubsub::testing::PubSubTestBroker;` и
`use ruststream::testing::TestApp;`.

`TestApp::start(app)` подключает приложение и монтирует его обработчики.
`tb.broker::<PubSubTestBroker>().message(&order).to("orders-workers").publish()` доставляет заказ в
подписку обработчика, а `tb.settle()` дожидается конца реакции.

`tb.broker::<PubSubTestBroker>().subscriber("orders-workers").assert_called_once()` дальше
проверяет, что обработчик отработал, а
`tb.broker::<PubSubTestBroker>().published::<Receipt>("receipts").assert_called_once().with(&expected)`
проверяет, что именно он опубликовал в тему. См.
[Юнит-тестирование сервиса через TestApp](https://powersemmi.github.io/ruststream/latest/guides/testing/#unit-testing-a-service-with-testapp).

Файл маршрутов монтируется на внутрипроцессный транспорт таким, каким поставляется.
`#[subscriber(GooglePubSub::new("orders-workers"))]` открывает внутрипроцессную подписку так же
легко, как открывает streaming pull, а `Publish` конструирует издателя на нём так же, как на
брокере. Ни на одной из двух сторон нет отдельного тестового написания, которое надо подставить.

`tb.out::<Marker>().with_options(&PubSubPublishOptions { ordering_key: Some("order-7".to_owned()) })`
читает обратно ключ, который запросила одна публикация через слот, а `assert_options_default()`
утверждает, что публикация ключа не назвала и взяла ключ точки монтирования. Ключ попадает и в
опубликованное сообщение - в тот самый заголовок `partition-key`, под которым его отдаёт доставка,
поэтому работает любая из двух проверок.

Внутрипроцессный транспорт маршрутизирует по одному адресу, имени подписки, потому что тем он не
хранит. Поэтому тест публикует в подписку, а не в тему. `batch_wait` соблюдается: пакетирование в
любом случае идёт на клиенте. `create_with_topic` нечего создавать, а `max_outstanding` и
`ack_extension` называют машинерию, которой здесь нет, поэтому все три настройки игнорируются.

Издатель, переживший `shutdown`, сообщает здесь `NotConnected` так же, как против Pub/Sub, поэтому
тест не может позеленеть на публикации, которую отверг бы боевой брокер.

То, что решает сам сервер - продление срока, время повторной доставки, упорядоченную доставку,
политики dead-letter, - проверяют против [эмулятора](#the-emulator), где работают интеграционный
набор и lifecycle из conformance фреймворка.
